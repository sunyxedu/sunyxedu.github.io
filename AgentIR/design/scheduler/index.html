    Scheduling and commitment¶

    The scheduler answers two different questions: can a request execute now? and can its result become part of the surviving program? Input readiness answers the first; guard resolution answers the second.

    Admission in one table¶

    Data Guard Scheduler behavior
    Missing True or pending Wait for dependencies
    Ready True Enqueue as committed work, at highest request priority
    Ready Pending Consider speculative issue within funding and physical capacity
    Any False Squash; cancel an active engine attempt
    Any Unmasked failure Fail the dependent work

    The runtime maintains a pending index rather than rescanning every historical record on every update. Decisions, data completions, hints, and capacity changes trigger reevaluation.

    Read the state correctly¶

    An engine record moves through states such as pending, issued, done, squashed, and failed. Commitment is a separate property. A speculative request can be done while waiting for a guard.

    There are separate completion and commitment futures. Eligible speculative descendants can use completed data before it commits, but public forcing and unknown-effect bodies wait for the appropriate commitment conditions.

    This is why “the request finished” does not prove “the result was published.” The ledger records both timing and final disposition.

    Bound speculative work¶

    The main controls are SpecConfig.window and max_spec_inflight:

    • The window bounds unresolved guard depth eligible for speculation. It does not count tokens or Python stack depth.
    • The budget limits concurrent funded speculative requests. It is distinct from an engine's total request capacity.

    depth1_unmetered=True exempts depth-one continuations from the speculative budget, but does not create physical engine capacity. Deeper work remains metered. A static plan can replace the global depth rule for matched decisions with per-decision bounds and sibling budgets.

    Among speculative candidates, the scheduler favors demanded work, shallower guards, lower rank sums, stronger dynamic hints, then registration order. Committed work takes precedence over all of them. When needed, committed requests can reclaim capacity from speculative attempts on the same engine.

    Effects have a separate execution lane¶

    Python op calls use a control-plane pool. Tool bodies use a dedicated pool and tool scheduler, avoiding a single FIFO queue that could trap committed work behind speculative tool calls.

    Unknown-effect operations wait for their guard and bound dependencies to commit. Unknown tools are fenced before body dispatch. Speculable tools can run early within the tool scheduler's own use of the window and budget settings.

    Runtime.run drains effect obligations before returning, including on exceptional exits, subject to its configured drain timeout. Runtime.submit is a lower-level asynchronous interface; it should not be treated as an interchangeable cleanup boundary. Closing a runtime releases the scheduler, pools, and engines.

    Cancellation does not change identity¶

    Cancelling an engine request aborts the physical attempt. If capacity preemption later allows it to run again, it uses the same logical node and seed with a new request ID. Old events are fenced from the new attempt.

    A losing guard is different: squashed work has no surviving obligation to reissue. A running Python tool may finish after cancellation because general Python callables cannot be forcibly interrupted; its result still cannot make a rejected branch commit.

    Retry the right failures¶

    Failure Current policy
    Committed engine request failure Up to three attempts in the request retry path
    Repeated speculative request failure After five failures, defer until commitment rather than fail an unresolved world immediately
    Deterministic projection failure Do not retry; defer publication while its guard is pending
    Unknown tool body failure No automatic retry
    Speculable tool body failure Up to three attempts per phase; commitment allows a fresh committed retry phase after speculative failures
    Physical engine death Fence all sibling attempts in that engine epoch, drain, and rebuild within the runtime restart limit

    The default engine restart limit is one. Engine death is process-wide, so treating it as a failure of only the request that noticed it would leave sibling requests attached to a dead process.

    A decision watchdog prevents a ranking or continuation condition that never resolves from leaving guards pending forever. Both decision and effect-drain timeouts are configurable.

    Keep optimization separate from semantics¶

    Expected-value funding, dynamic hints, cache prefetch, and speculative slot preemption alter admission or priority. They must not remove the obligation to execute a surviving node. A score bound that permanently truncates a candidate has a different contract; see prediction and optimization.
