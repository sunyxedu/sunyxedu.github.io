    Algorithms¶

    The built-in algorithms are ordinary AgentIR programs. They are useful both as runnable baselines and as examples of where weak control dependencies appear in an agent workflow.

    Run agentir list for the available names. Import implementations from agentir.algos, or select one with agentir bench --algo NAME.

    Choose a program structure¶

    Algorithm What it does Where overlap can appear
    self_consistency Sample answers, vote on extracted answers, optionally explain the winner The explanation can continue from candidates before the vote resolves
    best_of_n Sample candidates, score each with a judge, return the selected original answer Candidate generation and scoring overlap; this implementation has no final polish request
    heavy Generate several answers, use a comparative judge, continue from the selected answer The final continuation can overlap the comparative decision
    cascade Produce and review a draft, then select escalation or polishing behavior Alternative continuations can be constructed before the review selects one
    beam_search Repeatedly expand a bounded beam and select the next beam Next-round continuations can run under unresolved beam selections
    sal_beam Search by scored reasoning steps and aggregate completed answers Available overlap depends on step boundaries and materialization needed for scoring
    reflexion Review and revise until accepted or the iteration bound is reached Future iterations are traced under continue guards
    mcts Maintain search statistics, select a frontier, roll out, and backpropagate Finite frontier choices expose local speculation; iterations settle their state updates

    The table describes the checked-in implementations. Sharing an algorithm name with a paper does not establish identical prompts, scoring, or stopping rules.

    Read a representative algorithm¶

    Start with heavy.py if you want to see the complete generate–judge–continue pattern. Read self_consistency.py for Python value operations, and reflexion.py for loop.

    common.py supplies prompt construction, answer normalization, score parsing, and ranking helpers. These functions affect measured task accuracy: a successful model request can still yield an unparseable or incorrectly normalized answer.

    Scoring changes the dependency graph¶

    Beam search can score using log probabilities, judge generations, or a process reward model (PRM). These choices need different data:

    • Log probabilities come from the generation's observation mode. They must be requested as part of that node.
    • A judge continuation can often consume the candidate's symbolic spine directly.
    • A transformed PRM prompt may need concrete candidate text before it can be constructed. That creates a data barrier; cache prefetch can help prefill, but cannot erase the dependency.

    The SAL implementation also materializes step text for parts of its control flow. Do not assume every algorithm is entirely trace-ahead or accepted by the static compiler.

    Keep algorithm changes separate from scheduler changes¶

    Candidate count, beam width, stopping rules, scoring aggregation, token budgets, and bound_commit change the algorithm or its output contract. The speculation window, funding budget, and priority policies control how its graph is scheduled.

    For an A/B comparison of branch speculation, hold the algorithm fixed. In particular, if a valid bound allows early truncation, enable that same algorithmic rule in both arms. See benchmarking.

    Function defaults and CLI defaults can differ: for example, the shared CLI --k default is 6. Use the CLI reference and the function signature for the entry point you actually run.
