    Benchmarking¶

    A good benchmark answers three questions separately: did the two arms compute the same thing, which mechanism changed, and how much faster was it at the intended concurrency. agentir bench handles the mechanics; this page explains how to use it so the answer means something.

    Run the gates first¶

    agentir check --model Qwen/Qwen2.5-0.5B-Instruct \
  --algo beam_search --task gsm8k --offset 0 --runtime-graph check.svg

    check runs both verification gates on one problem and exits non-zero on any divergence. A speedup measured on a configuration that fails the gates is not a result.

    A paired run¶

    agentir bench --model Qwen/Qwen2.5-0.5B-Instruct \
  --task gsm8k --algo heavy --n 20 \
  --spec both --concurrency 1 \
  --out runs/heavy.jsonl --dump-ledger runs/heavy-ledgers --runtime-graph runs/heavy-timelines

    --spec both runs speculation off then on over the same problems with the same run seed and the same per-problem invocation key, so both arms sample the same tokens, then prints the paired summary: mean and percentile wall time, accuracy, answer agreement, committed and wasted tokens, speculative hit rate, and accumulated lead. The JSONL holds the metadata, arm summaries, and per-problem records.

    Other modes: --spec ladder adds the serial and oracle arms (see the ablation ladder); --spec fastbase adds a phase-serial beam baseline that batches decode and grading but forbids overlap between them.

    Hold everything else fixed¶

    Record, and keep identical between arms: model and revision, engine version and arguments, chat template and parser, sampling parameters, algorithm knobs, task slice, run seed, wire, and concurrency. For tools add the effect declaration, projection, predictor, and certificate. The bound-commit flag is an algorithm knob and must match in both arms, because it changes which losing-branch tokens exist.

    Speculation-only knobs (--judge-prefetch, --ev-gate, --spec-preempt, --depth1-unmetered, --prune-margin) apply to the spec-on arm only, so the off arm stays a pristine baseline. vLLM token drafting is an engine setting; if you vary it, vary it explicitly in both arms rather than folding it into "spec on".

    Choose the unit¶

    Question Profile
    Does one task finish sooner? paired per-task latency at --concurrency 1
    Does a loaded server finish more tasks? a fixed higher-concurrency throughput profile, reported separately
    What did the speedup cost? committed versus wasted tokens, request counts, engine time
    Is quality preserved? paired accuracy with a declared non-inferiority margin

    Warm-up, weight loading, and dataset download are separate phases; say which are timed. One task can contain dozens of overlapping requests, so per-request latency, per-task latency, and suite makespan are different numbers.

    Summarize honestly¶

    agentir.bench.stats provides the paired analysis the formal scripts use: per-task aggregation in log-latency space, a cluster bootstrap over tasks for the geometric-mean speedup interval, a paired sign-flip test (exact up to 16 tasks, Monte Carlo above), Holm correction across hypotheses, and quality non-inferiority whose lower confidence bound must exceed the negative margin. The task is the statistical unit; repetitions within a task are aggregated first.

    Decide the analysis before looking at the results, keep the raw records, and tie every summary to the configuration and artifact hashes that produced it. The frozen protocols in the experiment archive are examples of that discipline.

    Source: bench/runner.py, bench/stats.py, bench/tasks.py.
