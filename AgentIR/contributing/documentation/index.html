    Work on the documentation¶

    The manual is an English MkDocs site using Material for navigation, search, syntax highlighting, and responsive layout. Content lives in docs/; the build does not import vLLM or require a GPU.

    Preview locally¶

    From the repository root:

    python3 -m venv .venv-docs
source .venv-docs/bin/activate
python -m pip install -r requirements-docs.txt
python -m mkdocs serve

    Open the address printed by MkDocs, normally http://127.0.0.1:8000/AgentIR/. The /AgentIR/ prefix mirrors the configured project-site URL. Editing a page rebuilds the preview.

    Build and check¶

    python -m mkdocs build --strict
python scripts/check_docs.py

    The build writes the static website to site/. Strict mode checks navigation and Markdown links. The additional checker validates generated local links and fragments, repository source links, English article content, Python snippet syntax, public API coverage, and the engine-free compilation tutorial. It does not run GPU examples or fetch datasets.

    The documentation workflow runs these commands and uploads the site as a build artifact. It does not publish automatically.

    Publish the website¶

    The live manual is hosted at hemlix.me/AgentIR/. Its static output is published in the AgentIR/ directory of the sunyxedu.github.io repository, whose existing GitHub Pages configuration serves hemlix.me.

    After a successful strict build and documentation check, replace that directory with the contents of site/, review the generated-file diff, and commit and push it to the website repository's master branch. Keep the site's root homepage, résumé, and CNAME intact. Wait for the Pages deployment to succeed and check the live overview, a nested page, and search assets before announcing publication.

    The AgentIR repository keeps the editable documentation source; the website repository keeps the published build. Both commits should identify the same documentation release. To host elsewhere, update site_url before building so canonical URLs and sitemaps use the actual origin.

    Put information where readers expect it¶

    Section Reader's question Writing approach
    Start here What is this system, and how do I run one program? Introduce architecture, then one complete example
    Build programs How do I accomplish a task? State prerequisites, show code, explain its result
    Understand the design Why does this behavior hold? Explain invariants and the implementation choices enforcing them
    Verify and measure How do I know it is correct or useful? Separate evidence, interpretation, and limits
    Reference What is the exact contract or default? Group related names; make constraints easy to scan
    Contribute Where is the code, and how do I change it? Map behaviors to source and focused tests

    The organization borrows the staged, diagram-led navigation of AFL++, the compact concept–example–topic progression of tradingflow, and the separation of learning, reference, and deeper topics in Rust's documentation index. The diagrams and AgentIR explanations are original to this manual.

    Keep the presentation quiet¶

    Use one purpose per page, short introductory paragraphs, descriptive headings, and tables only for genuine comparisons or mappings. Explain a term before relying on it. Keep configuration inventories in reference pages and place important caveats beside the feature they qualify.

    The stylesheet uses local system fonts and a restrained light palette. Diagrams are versioned SVG with accessible titles, descriptions, and Markdown alternatives. The overview's stage links work with normal browser navigation and keyboard focus. A small overrides/partials/source.html template keeps the repository link static, without fetching GitHub statistics. Avoid external diagram renderers or fonts that make reading depend on another service.

    Keep examples and contracts current¶

    Check the implementation and relevant tests before editing a behavior claim. Prefer the supported root exports; use canonical modules for advanced APIs. Label partial snippets and illustrative schedules. Never present an unexecuted GPU example as a measured result.

    requirements-docs.in declares direct build dependencies; requirements-docs.txt pins their resolved dependency set. To refresh it with uv:

    uv pip compile requirements-docs.in -o requirements-docs.txt

    Rebuild strictly and repeat the browser checks after changing theme dependencies, layout, diagrams, or navigation. Check desktop and narrow mobile screens, search, sidebar navigation, keyboard focus, code copying, and the deployed subpath.

    Preserve research records¶

    Frozen preregistrations and the historical compliance retrospective stay in the repository. They are excluded from the public site's page and search indexes through exclude_docs; the experiment archive supplies English context and links to the relevant records.

    Do not rewrite a preregistration to match a new experiment. Create a new versioned protocol, and update the archive map. Current backend guides should describe current code rather than inheriting older protocol assumptions.
