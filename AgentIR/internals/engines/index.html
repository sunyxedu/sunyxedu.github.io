    Engine adapters¶

    The scheduler never touches vLLM directly. It talks to an engine adapter with one method, stream(...), plus warm, tokenizer, restart, and shutdown. Three adapters implement that interface. This page explains what the scheduler needs from an engine, how each adapter provides it, and how prompts are represented on the way in and out.

    The contract¶

    async for event in engine.stream(
    prompt=atoms,            # str on the text wire, list[int] on the token wire
    params=frozen_params,    # the validated, identity-bearing sampling parameters
    seed=record.seed,        # derived from the NodeId
    priority=depth_or_zero,  # 0 for committed work, guard depth for speculation
    request_id=attempt.id,   # fresh per attempt, never reused
    want_logprobs=..., want_token_ids=..., event_granularity="delta" | "final",
):
    ...

    Cancelling the consuming task must abort the request in the engine. Every event is a StreamEvent with text, token ids, logprobs, top-k alternatives, finish and stop reasons, prompt and cached token counts. Consumers aggregate events, so a "final" delivery (one terminal event) and a "delta" delivery (one event per engine step) commit identical bytes; granularity changes host overhead, never semantics.

    Each scheduler action maps onto one engine call:

    Scheduler action Engine call
    committed or speculative issue generate(prompt, SamplingParams(seed=...), request_id, priority=0 or depth)
    squash or preempt cancel the task; the generator's cleanup aborts the request exactly once
    fork of a parent's output nothing special: vLLM's prefix cache reuses the parent's KV blocks, and num_cached_tokens reports it
    logprob scoring SamplingParams(logprobs=k)

    vLLM's priority queue serves smaller values first, which is why committed work is 0 and speculation is its positive depth. Sibling draws of an expand are separate requests on purpose: vLLM's n>1 derives child seeds arithmetically from the parent's, and AgentIR sibling seeds are independent digests.

    Wires: what an atom is¶

    The IR is generic over atoms. Two wires exist, chosen per runtime with wire="text" or wire="tokens".

    Wire Atoms Prompt reaches the engine as Use when
    text (default) str a string the engine tokenizes plain completion programs; judge-server scoring
    tokens tuple[int, ...] a TokensPrompt id array tool loops and chat boundaries that must survive without a decode/re-encode round trip

    On the token wire a continuation is an exact token-level prefix of its parent, so the cache hit is exact; on the text wire it degrades only at block boundaries. The tokenizer comes from the engine itself. With several engines on a token wire, the runtime certifies at warm-up that their tokenizer programs are byte-identical (a fingerprint of the fast tokenizer's backend JSON plus special-token ids), not merely the same vocabulary size.

    The exact stream text is kept as a sidecar alongside token ids: vLLM may return special or stop tokens while omitting them from the text, and out_text must return what the engine actually said.

    In-process vLLM¶

    VLLMEngine owns an AsyncLLMEngine built with prefix caching and priority scheduling. Weights load on first use, once, on the loop thread. Device pinning sets CUDA_VISIBLE_DEVICES only during that construction window, so two engines can live on different GPUs in one process.

    The first thing the adapter does after construction is a capability handshake. It records the vLLM version, resolved engine args, parser configuration, and drafter settings, and fails fast on missing correctness-critical capabilities: generate and abort must exist, RequestOutputKind.DELTA must exist, and the version must match the pinned expected_version (0.24.0 by default), because version drift invalidates any byte-equality certification. Optional capabilities missing (such as FINAL_ONLY delivery) only disable the corresponding optimization.

    The engine key that deduplicates physical engines digests the whole resolved configuration: model, devices, reasoning parser, token drafter, and every engine argument. Two EngineSpecs with the same model but different memory limits are two engines.

    Judge server subprocess¶

    Two in-process engines share one Python interpreter, so at small model scale their host loops serialize on the GIL: one engine's sampler and detokenizer sit between the other's decode steps. make_runtime(judge_process=True) instead launches the judge role as a vllm serve-style subprocess with its own GIL and CUDA context, speaking the OpenAI /v1/completions endpoint. That is all a process-reward sweep needs: one greedy token per step whose top-k alternatives arrive as top_logprobs.

    Readiness is fail-closed: health, served-model identity, version pin, and a contract probe that requests one token with full top-k and checks the response shape. The subprocess is reaped synchronously in Runtime.close so the next benchmark arm never races a dying server for GPU memory. This mode is text-wire only.

    Certified remote vLLM¶

    make_remote_runtime keeps the tracer and scheduler on the client and moves everything model-specific to a vLLM 0.24 server: tokenization, chat rendering, generation, and tool-call parsing. The client needs no vLLM and no tokenizer; it uses only the standard library.

    The protocol is three server-owned routes plus the native token-in/token-out generate route:

    Step Route What it does
    handshake GET /v1/agentir/tier1/certificate Returns a canonical JSON certificate of the model revision, tokenizer, chat template, parser classes, and structured-output settings, with a digest header and an instance id
    render POST /v1/agentir/tier1/render Turns messages plus tool schemas into exact prompt token ids and the server's complete SamplingParams, after the parser's adjust_request
    generate POST /inference/v1/generate Token-in, token-out streaming
    derender POST /v1/agentir/tier1/derender Re-renders the original request, checks digests, and runs the completed-output parser

    Every protected request carries the certificate digest and instance id as headers; the server answers 412 or 428 if they do not match, and the client treats that as engine death and re-handshakes. The render result is frozen into the E-node's parameters as a _remote_tier1 envelope, so the server's exact sampling identity is part of the NodeId. Successful renders are memoized in a small single-flight LRU keyed by certificate, instance, and canonical request.

    The server side is agentir.execution.vllm_certificate.middleware, loaded with vllm serve --middleware .... It builds the certificate only from vLLM's resolved application state and refuses to serve if the parser combination is outside the audited set.

    Remote mode is terminal-only: tool calls are published after generation and derendering finish, not mid-decode. Tools and the tool loop explains what that costs.

    Model roles¶

    Programs name roles, not models: infer(x, model="judge"). A Runtime maps roles to ModelSpecs, each binding an engine spec and canonical chat-template arguments. make_runtime creates main and aliases judge to it unless you pass judge_model or judge_devices. The same beam-search program therefore runs single-engine or with a dedicated verifier engine depending only on configuration.

    Runtime.chat_prefix(messages, role=..., tools=...) renders through the role's own template and tokenizer (or the remote render route), returning a string or token tuple to pass to lit. Harmony models (GPT-OSS) render through vLLM's Harmony stack and require the token wire.
